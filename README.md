# 🔗 CrossLink: Breaking Location Privacy by Linking Device Identifiers Across Protocols

This repository contains the artifact for the ACM CCS paper **CrossLink: Breaking Location Privacy by Linking Device Identifiers Across Protocols**. CrossLink is a passive cross-protocol tracking framework that links temporary identifiers emitted by the same device over LTE, WiFi, and BLE. The artifact supports the simulation, tracing, reconstruction, and plotting pipeline used in the paper.


## Paper Overview

Smartphones simultaneously transmit temporary network identifiers over LTE, Wi-Fi, and BLE to facilitate network association and service discovery. Per-protocol identifier randomization assumes that privacy protections compose independently across protocols. CrossLink demonstrates that they do not: even under fully passive eavesdropping and noisy spatiotemporal localization, unsynchronized identifier rotations enable cross-protocol stitching of device trajectories over time.

## Implementation overview

Our **CrossLink** implementation is centered around the _pipeline_, which is essentially a set of _tasks_ that execute sequentially, such as SUMO simulation, trace generation, sniffer observation generation, intra-protocol mapping, graph generation, etc. The pipeline accepts a _config_ as input, which points to a config file describing the information required for individual tasks, such as input filenames, algorithm parameters, user count, etc.

Concretely, a task can be either a SUMO run, a Python script or a Rust program. To avoid typing all the commands for each task, we have provided a `Makefile` that contains targets which run the entire pipeline with specific configs. This should be the main entry point for whoever looking to try out CrossLink or to replicate results.

Detail on config format can be found at [**`CONFIG.md`**](CONFIG.md).

## Preparing for a run

We implemented CrossLink part in Python and part in Rust. We tested the pipeline against **Python 3.10** and **Rust 1.85.1** on **Debian 13** (`6.12.107+deb13-amd64`) with **SUMO 1.18.0**. In theory, CrossLink can also run on Windows and macOS, but SUMO installation will need to be taken care of manually.

Additionally, you also need to install the `time` package (for Debian, name might differ for other distro, same hereafter) for measuring run time; `build-essential` and relevant packages for building Python wheels. Required Python packages are recorded in `pyproject.toml` and can be installed using `uv`.

We recommend running CrossLink on fast enough hardware (e.g., with 8 cores) as a few steps greatly benefit from parallel processing. Memory usage can get high for configs with large user count (e.g., 512 or 1024). We recommend reserving at least 16GB for such runs. Intermediate files generated by individual steps can also get large for large user count, so make sure you have sufficient free disk space proportional to your user count. For reference, runs with 512 users can generate ~25GB of intermediary and final output files.

To make things easier, we have also provided a `compose.yml` with which you can immediately pull up a docker container with all required software dependencies installed. The repository itself will be mounted at `/data` inside the container. In the following guide, we will assume that you are using this container. If you are using an alternative setup, make sure that the correct Python environment has been activated.

```bash
# pull up the docker container
# this will automatically build the image from Dockerfile
docker compose up -d

# connect to the container
docker exec -it ${CONTAIENR_NAME} bash

# run commands inside the container
# code repo is mounted at /data r/w inside the container
# container itself is Debian based so you can also install any package you need via apt
make clean
```


## Running a minimal config

We provide a minimal config ("smoke test") with 32 users for prototyping and quick verification of environment setup. To run this config, clone the repository, pull up the sample docker container, run first the `mobility_data` target to generate simulation data, then run the `smoke_test` target to run the rest of the pipeline:

```bash
# clone the repository
git clone https://github.com/aneetdutta/CrossLink_CCS.git crosslink

# pull up the docker container and enter it
cd crosslink
docker compose up -d
docker exec -it ${CONTAINER_NAME} bash

# enter the repo dir and generate the mobility data
cd /data

# run the pipeline
make mobility_data
make smoke_test
```

If you are not using the provided docker container, make sure to update the path to the repository dir in `rust_code/config.yaml` before running any target:

```yaml
root_dir: "/data"  # repo dir
```

## Running a 512 user config

This is similar to the size that we used in our experiments for the paper. We provide a baseline config for such experiment named `scenario_result_512_sumo_all1`. To run this config, invoke the `baseline` target in the makefile:

```bash
make baseline
```

Likewise, you should first see SUMO simulation output with many warnings of pedestrians and vehicles teleporting, then outputs from different tasks in the pipeline. The process can take up to 1 hour to complete.

Results are saved in the same location as smoke test, except now with config name `scenario_result_512_sumo_all1`.



## Validation with real-world measurement

Apart from simulation, we have also collected LTE and BLE packets from 12 commodity devices to evaluate CrossLink's effectiveness in real-world settings. These traces are placed under `real_world/`:

- `lte_observations.csv`: Passive LTE sniffer captures.
- `ble_observations.csv`: Passive BLE advertisement captures.
- `anchors.csv`: Mix-zone entry/exit mappings.
- `ground_truth.csv`: True device identity mappings.

To run the evaluation, inovke the `validate_real_world` target in the makefile:

```bash
make validate_real_world
```

You should see message reporting successful completion. Results are stored also under `real_world/output/images/`.

## Running individual tasks

If for any reason you need to run individual tasks inside the pipeline, refer to the following pipeline dissection. In general, you need to specify the config name and the task name to the correct entry point program. The intermediary files can be found most often under `data/${CONFIG_NAME}`. The estimation of run time assumes that you are using the `scenario_result_512_sumo_all1` config on an 8-core Zen 4 system.

```bash
# specify the config name and dervied scenario name
# config name is used for Python tasks
# scenario name is used for Rust tasks
CONFIG=scenario_result_512_sumo_all1.yml
SCENARIO=$(basename "$CONFIG" .yml)

# mobility simulation and trajectory filtering (20-25 minutes)
python3 main.py -c "$CONFIG" -t sumo
python3 main.py -c "$CONFIG" -t filter_users_polygon
python3 main.py -c "$CONFIG" -t filter_users_RI_Count

# generate user data (e.g., identifiers) (~1 minute)
python3 main.py -c "$CONFIG" -t generate_user_data

# generate protocol observation (sniffer samples) (~1 minute)
cd rust_code && cargo run --release -- "$SCENARIO" generate_sniffer_data

# aggregation (~1 minute)
python3 main.py -c "$CONFIG" -t aggregate_new

# inter and intra protocol mapping, primary (1-2 minutes)
cd rust_code && cargo run --release --features inter_map_disable_trim -- "$SCENARIO" inter_map
cd rust_code && cargo run --release --features intra_map_disable_trim -- "$SCENARIO" intra_map

# refine inter and intra protocol mappings found previously (~2 minutes)
python3 main.py -c "$CONFIG" -t refine_intramap
python3 main.py -c "$CONFIG" -t intra_filter

# reconstruct traces (~40 minutes)
python3 main.py -c "$CONFIG" -t reconstruction

# plot the figures (~1 minute)
python3 main.py -c "$CONFIG" -t plot
```
